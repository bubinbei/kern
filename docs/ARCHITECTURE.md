# Контракт ядра

Статус: целевая архитектура; реализован первый raw-срез 0.1.0, не все описанные механизмы. Ядро не зависит от графиков или конкретного прибора. Реализованное/ограничения: [руководство](CORE_GUIDE.md), [контракт 0.1](CORE_INTERNALS.md), [проверка](CORE_VALIDATION.md).

## Путь данных

Источник → проверка ядром → обязательный сырой журнал → интерпретатор → проверка результата ядром → журнал результатов → графики и рабочие файлы. Приём в память и подтверждённая запись на диск — разные события. Уведомление о приёме не обещает сохранность при аварии.

Таблица сырых каналов и таблица параметров — согласованные снимки последнего состояния. История хранится в упорядоченных событиях, а не в периодических копиях таблиц. Пакет одного источника применяется согласованно; близкое время приёма разных приборов не означает одновременное измерение.

Утверждены redb для внутреннего хранилища ядра и uPlot для заменяемого веб представления графиков. Три логических набора: входы, неизменяемые версии калибровок и результаты; история, реестр/активации и позиции потребителей хранятся дополнительно. Ядро — единственный писатель, все плагины работают через его API. Выбранные части уже реализованы в отдельном [прототипе](PROTOTYPE.md), старый KJN backend сохранён. Переход и приёмка: [STORAGE_CHARTS_PLAN](STORAGE_CHARTS_PLAN.md).

## Реестр и качество

Стабильные ID источника/канала/параметра не меняются при отключении или расширении. Резерв — 100 адресов на экземпляр источника, первоначальная цель до 10 экземпляров; передаются только занятые каналы. Номер в UI не заменяет устойчивый ID. Выход за резерв — новый экземпляр с отдельным подключением; один COM-порт принадлежит одному экземпляру. Разные экземпляры одного типа используют разные порты. Источник из 18 каналов может добавить ещё 6 без сдвига 20 каналов другого источника.

Значение типизировано: целые счётчики не округляются в float. Вместе с ним идут источник, сессия, последовательность, время измерения/приёма и качество. Новый равный отсчёт, старое значение, пропуск и отключение различаются. Дедлайны монотонные, календарная привязка отдельная; часы разных процессов не сравниваются без согласованного преобразования. Истечение срока обновляет качество даже при отсутствии новых пакетов. Ошибочные/чужие/старые сообщения отклоняются с диагностикой.

## Единое состояние и карты

Диспетчер ядра — единственный писатель авторитетного состояния. Интерпретатор определяет смысл своей карты, ядро хранит полные неизменяемые версии; у интерпретатора рабочая копия. Прямых ссылок между плагинами нет. Клиенты получают согласованный snapshot с позицией, затем события после неё; пропуск требует явной пересинхронизации.

Изменение: черновик с expected revision → проверка структуры ядром и семантики обработчиком → фиксация полной версии на диск → подтверждение загрузки интерпретатором в его текущей сессии → фиксация активации с точной границей входной последовательности → новые задания. Сохранено не означает применено. Конкурирующий старый черновик не затирает новую карту. Повтор request ID не выполняет команду второй раз.

Каждое задание/результат содержит ID и версии карты/алгоритма. Поздний ответ старого задания проверяется против его версии. Replay использует исторические карты, не текущую. Полная карта пишется при создании/изменении; отсчёт ссылается на revision. Состояние осреднения и контрольные позиции сохраняются отдельно. При рассинхроне расчёт затронутых входов приостанавливается, сырой журнал продолжается.

## Журнал и восстановление

Обязательный локальный журнал — компонент ядра, а не отключаемый экспортёр. Он сохраняет принятые входы, результаты, версии и границы активации. Версионированные записи/сегменты имеют длину и контроль целостности; повреждение хвоста не разрешает молча переписать исходник. Читатель различает целый префикс и аварийный хвост. Подтверждение сохранения выдаётся после согласованной фиксации на диск.

Интерпретатор и каждый писатель имеют собственную подтверждённую позицию. После перезапуска недостающие параметры пересчитываются из входов, затем файлы догоняются без перестановки и дублей. Повторы допускаются в транспорте; устойчивые ID и контрольные позиции предотвращают повторный эффект. Для вычисления со состоянием нужен checkpoint либо достаточная предыстория. Граница replay/live общая, новые строки не опережают старые в одном потоке.

Резервный плагин дополнительно копирует события и все необходимые исторические метаданные через ядро, включая подключение позднее начала записи. Копия восстанавливается без исходного профиля; версия специального алгоритма тоже должна быть доступна. Вторая копия на том же диске не защищает от отказа диска. Квоты и очистка не удаляют ещё нужные версии. Сначала запись без сжатия; сжатие независимых сегментов — позже по измеренному бюджету, без задержки сырого приёма.

## Изоляция и надзор

Источники, интерпретатор и писатели — отдельные процессы с ограниченными очередями/сообщениями. Зависший обработчик не держит общую блокировку. Heartbeat дополняется прогрессом и маркером из того же рабочего обработчика; ответ служебного потока не доказывает живой расчёт. Нет входов — не повод объявлять зависание. Маркер проверяет выполнение пути, не физическую правильность результата; значения проверяет независимый эталон.

Ядро перезапускает только свои процессы с ограничением попыток/задержкой, новой сессией и диагностикой. Постоянная ошибка переводится в явное состояние, без бесконечного restart. При переполнении или ошибке диска политика явная: ограничение приёма/разрыв и потеря с учётом счётчика; нельзя одновременно обещать бесконечный приём, ограниченную память и отсутствие потерь при отказавшем диске.

Обязательная системная оболочка — отдельный клиент: меню, настройки, плагины и минимальные статусы. Измерения между плагинами идут через ядро, не через UI. Штатное закрытие окна не вызывает respawn; аварийное зависание допускает ограниченный restart и safe mode без потери профиля. Закрытие UI не останавливает регистрацию; полная остановка — отдельная команда.

Графики — отдельный заменяемый пакет с uPlot и ограниченным bridge через Rust-host; первый host включён как локальный Rust HTTP-процесс с окном установленного Edge/Chrome; окончательный встроенный WebView ещё не выбран. Системная нативная оболочка сохраняется на время прототипа. Частоту приёма не связывать с FPS. Перерисовывать по событиям/дедлайну и только видимое; данные для экрана агрегировать с сохранением экстремумов/разрывов, без изменения архива. Кэшировать сетку/подписи, скрытые экраны не работают фоном. Динамический SDK для произвольных рендеров — после проверки базовых границ.

## Текущая оболочка и будущее веб направление

Первый нативный срез оболочки/пакетов реализован отдельно от ядра. Веб среда для операторских экранов без программирования — самостоятельное последующее направление; ответственные участки остаются Rust-процессами. Формат папок, реальные границы надзора и порядок развития: [PLUGINS](PLUGINS.md).

## Будущие сервер и рабочие места

Один сервер KERN владеет оборудованием, данными и расчётом; локальный оператор, браузеры и KERN в режиме клиента используют общий версионированный контракт. Общие веб экраны переиспользуются между рабочими местами. Отдельный необязательный веб шлюз изолирует сеть от цикла регистрации; существующий локальный IPC не публикуется наружу. Просмотр и сервисное управление разделены полномочиями, команды проверяет ядро, изменения версионируются и протоколируются. Удалённый оператор получает отзываемое право управления; обрыв связи не останавливает запись. Это будущий план, не сетевые возможности текущей сборки: [NETWORK_PLAN](NETWORK_PLAN.md).
