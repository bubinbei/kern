# Восстановительный резерв

Настройки доступны через единственную кнопку ⋮ → «Восстановительный резерв». Выберите папку системной кнопкой «Выбрать…» либо введите абсолютный путь. «Папка профиля» возвращает стандартное расположение. Изменения действуют после «Сохранить»; «Отмена» отбрасывает черновик. «Перечитать» получает сохранённую версию; устаревшее окно не может затереть новую версию.

| Режим | Запись | Назначение |
|---|---|---|
| Без сжатия | `events.jsonl` | Минимум вычислений, больше места |
| Быстрое · слабый ПК | `events.kbk`, Zstd −3 | Начальный кандидат для Celeron J4125 |
| Сбалансированное | `events.kbk`, Zstd 1 | Умеренное сжатие |
| Компактное | `events.kbk`, Zstd 3 | Больше вычислений ради меньшего файла |

Сжатие однопоточное, без фонового пула Zstd. Уровень 0 Zstd не используется как «отключено»: у библиотеки он означает стандартный уровень. Режимы не обещают определённой скорости или степени сжатия; приёмка на J4125 впереди. Алгоритм и лицензии: [Zstd](https://github.com/facebook/zstd), [перечень зависимостей](dependencies.json).

По умолчанию сохраняются прежние `profile/backup/events.jsonl` без преобразования. Во внешней папке создаётся `kern-<profile_id>`: разные профили не смешиваются. Форма показывает фактический файл и файл по сохранённым настройкам отдельно, подтверждённую позицию / известную границу истории, размер и последнюю ошибку. Статус старше пяти секунд подписан как последний известный, без обещания продолжающейся записи.

Плагин проверяет настройки раз в 500 мс. Смена уровня между тремя режимами Zstd применяется к следующим блокам того же файла. Смена папки либо переход JSONL ↔ KBK открывает другой файл и догоняет всю доступную историю ядра с его подтверждённой позиции. Перед продолжением сверяется последнее событие с ядром. Старые файлы не удаляются и не переписываются; занимают место отдельно. При ошибке новой папки уже работающий писатель продолжает прежний файл с видимым предупреждением. При недоступном сохранённом пути во время старта плагин сообщает ошибку запуска; автоматического выбора другой папки нет. Смена папки не является миграцией основного redb. Копия на том же носителе не защищает от его отказа.

Все события ядра сохраняются без прореживания: исходные данные, версии/активации карт, результаты и прочие события журнала. Отдельных периодов записи этим срезом не добавлено. Библиотека пользовательских наборов, настройки линии, оформление и собственные настройки резерва пока не входят в журнал ядра/экспорт; резерв не является копией всей установки. `backup-settings.json` принадлежит профилю, обновляется атомарно с проверкой revision; `backup-status.json` — необязательная телеметрия, не источник измерений.

## Формат и восстановление

KBK v1 начинается с 8 байт `KERNBKP1`. Каждый независимый блок имеет 32-байтовый заголовок little-endian: `BLK1` (4), codec (1: 0 — исходный, 1 — Zstd), level (i8), reserved (2 нуля), plain_len (u32), stored_len (u32), CRC32 исходного payload (u32), last_sequence (u64), CRC32 первых 28 байт заголовка (u32). Payload содержит прежние пары JSONL «HistoryEvent + _commit/CRC». Если сжатие увеличивает размер, блок хранится исходным. Уровни могут различаться внутри одного файла.

Пределы до выделения памяти: исходный блок ≤1 МиБ, сохранённый ≤2 МиБ, окно декодера ≤2 МиБ. Проверяются заголовок, длины, CRC, порядок и метки событий. Это обнаружение повреждений, не криптографическая подпись. Полностью повреждённый блок даёт отказ. Недописанный последний блок исключается; писатель сначала сохраняет его точные байты в отдельный ASCII-файл `events.tail-<id>.bin`, затем продолжает подтверждённый префикс. Позиция публикуется только после `sync_all`. Память ограничена размером блока, весь архив не загружается в RAM; стартовая проверка последовательно читает архив целиком и на большой истории может занять время.

Одна команда автоматически определяет JSONL/KBK:

```powershell
kern-core.exe restore --input PATH_TO_EVENTS_FILE --profile NEW_PROFILE_PATH
kern-core.exe check --profile NEW_PROFILE_PATH
```

Нужна новая папка и совместимая версия KERN/алгоритмов. Исходный резерв не меняется. Успешное восстановление недописанного хвоста явно сообщает `uncommitted_tail: true`; ошибка оставляет `import-incomplete`, запрещающий открывать частичный профиль как завершённый. Общий drain вторичных писателей при полной остановке по-прежнему отдельная задача: подтверждённая история ядра может быть новее резерва.

Выбор папки выполняет отдельный краткоживущий процесс нативной оболочки. Одновременно разрешено одно такое окно на профиль, ожидание ограничено 120 секундами; остановка host завершает только свой helper. Сбор данных и heartbeat обязательной оболочки не ждут окна. Системный API: [SHBrowseForFolder](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shbrowseforfolderw).

Проверка: `cargo test --workspace --locked`, `python tools/validate_backup_settings.py`; независимое сравнение событий после восстановления всех режимов, обрыв/CRC, горячая смена папок/уровней, недоступный путь, старые версии, форма и системное окно. [Отчёт](validation/backup-settings-20261025.json). Слабые ПК, отключение питания и длительная запись ещё не приняты.

## Оценка целевого объёма — предложение, не новая настройка

25.10.2026 исследована локальная выборка 3000 событий за 330,305 с. При прежнем потоке короткий замер роста несжатого резерва даёт около 49 ГБ за 30 суток; 84% JSON в выборке приходится на результаты интерпретатора. В 96,6% соседних записей одного параметра значение и качество совпадают, но время/прочие поля могут отличаться: удалять такие записи целиком нельзя.

Офлайн-сжатие этой выборки Zstd 1 даёт ориентиры: короткие блоки, сгруппированные по времени, ≈3,3 ГБ/30 суток; блоки 256 КиБ ≈1,9 ГБ; только исходные события без parameters_stored при 256 КиБ ≈0,44 ГБ. Это экстраполяции одного текущего потока, без месячной/ресурсной приёмки. Последний вариант не является проверенным восстановительным форматом: нынешний restore требует результаты и непрерывную последовательность событий.

Рекомендуемый следующий эксперимент — двоичное представление, словари ID/единиц, сохранение различий отдельных полей без потерь (включая время, качество и причины), затем Zstd 1 блоками 64–256 КиБ. Для накопления блока нужен подтверждаемый на диске незавершённый хвост; нельзя держать час единственной копии в RAM. Ротация по часу/суткам упрощает обслуживание, сама по себе размер не уменьшает. Данные экрана могут быть прорежены для рисования, поэтому не подходят как источник полного резерва. Хранение одних входов с пересчётом результатов — отдельный возможный режим после проверки версий алгоритмов, исторических карт, времени, ручных действий и состояния расчётов. Ни удаление результатов, ни ограничение частоты этим обсуждением не включены. Бюджет 1 ГБ/месяц необходимо привязать к числу каналов/частоте/составу событий; при превышении сообщать прогноз, не терять данные молча.

### Уточнённая схема следующего формата

Согласованное направление: все сырые отсчёты + полный снимок рассчитанных параметров раз в 10 с; новый файл каждый час, новая папка каждые сутки. При применении новой версии калибровок текущий файл также закрывается, следующий начинается с полного снимка действующих карт и причины смены, например «В 14:25 оператор изменил калибровку веса». В служебных полях нужны точное время/граница событий и старая/новая ревизии. Имена остаются ASCII, например `2026-10-25/14-25-00_calibration-42.kbk`. Следующая часовая граница сохраняется. Для автономного восстановления расчётов с памятью понадобится начальный снимок их состояния. Это план: текущий KBK v1 так ещё не работает.

В той же выборке после отбора 34 последних результатов по десятисекундным корзинам и сохранения всех 1500 сырых пакетов Zstd 1 даёт ≈16,4 МБ/сут при 256 КиБ, ≈18,2 МБ/сут при 64 КиБ; соответственно ≈0,49–0,55 ГБ за 30 суток. Условия: около 30 сырых каналов, примерно один отсчёт/с на канал, около 30 выходных параметров. Это офлайн-оценка содержимого без дополнительных шапок/снимков состояния и смен калибровок, не готовый импорт. Предварительный бюджет с запасом — 20–30 МБ/сут (0,6–0,9 ГБ/30 суток), требующий проверки нового писателя и реального полного дня.
