# Текущий технический контракт ядра 0.1

Это описание реализованного среза, а не замена целевой [архитектуры](ARCHITECTURE.md). Для первого знакомства — [руководство](CORE_GUIDE.md).

## Состав

| Crate | Назначение |
|---|---|
| `kern-protocol` | Типы, версия API, ограниченные IPC-кадры и клиент |
| `kern-engine` | Единственный владелец состояния и потоковое чтение/запись журнала |
| `kern-core` | Процесс-сервер, команда состояния/остановки/проверки/восстановления |
| `kern-demo` | Отдельный синтетический источник; зависит только от protocol и JSON |

Ни GUI, ни библиотек приборов в ядре нет. Безопасный Rust: `unsafe_code = forbid`. Tokio, webview, графический цикл и постоянный таймер не используются. Диспетчер и дисковый поток в простое ждут сообщения; принятие TCP-соединения блокирующее. При остановке ядро само будит accept, не сканирует процессы пользователя.

## IPC v1

Сервер слушает только loopback; порт по умолчанию выдаёт ОС. `endpoint.json` содержит version/address/token/pid, не является долговременным состоянием и не коммитится. Токен 32 случайных байта создаётся заново при запуске. Его не выводят в консоль. Владение профилем защищено OS file lock, а не существованием lock-файла/PID. Это локальный интерфейс доверенных клиентов; разграничение прав отдельных плагинов и проверка ACL Windows ещё не реализованы.

Кадр: длина JSON в `u32 little-endian`, затем UTF-8 JSON. Один запрос/ответ на TCP-соединение. До выделения памяти проверяется длина: запрос 1–65536 байт, ответ до 524288. Чтение/запись запроса ограничены таймаутами; обработчик ждёт результат до 5 с. После таймаута запись могла завершиться — результат считается неопределённым, не отменённым.

Конверт: `version`, `token`, `request`. Команды request:

| `command` | Дополнительные поля | Ответ/эффект |
|---|---|---|
| `status` | — | Статус подтверждённого состояния, pending и disk_error |
| `snapshot` | — | Согласованный снимок сырых каналов + пустые parameters и позиция |
| `open_source` | id, resource, channels, expected_catalog_revision | Записанные slot/session/catalog_revision |
| `ingest` | batch | `durable` только после sync либо подтверждение точного повтора последнего пакета |
| `close_source` | id, session | Закрытие текущей сессии |
| `set_settings` | expected_revision, settings | Подтверждённая версия настройки свежести |
| `stop` | — | Запись остановки и выход; при disk_error выход без ложного durable |

Источник: ID 1–64 ASCII-символа `a-z A-Z 0-9 - _ .`, ресурс 1–64 ASCII без пробелов/управляющих символов, регистр ресурса нормализуется. Каналов 1–100, ID 0–99 уникальны, имя 1–128 UTF-8 байт. Резерв 100×10, слот сохраняется за ID. Активный ID/ресурс нельзя открыть повторно; автоматического освобождения зависшего источника пока нет. Явное close либо перезапуск ядра освобождает сессию.

Batch: source/session/sequence/measured_unix_ms/samples. Последовательность начинается с 1 и растёт на 1; время источника не используется как номер. Sample: channel, quality (`good/bad/missing`), value. Значение — типизированный `float/signed/unsigned/boolean`; float конечный, missing соответствует отсутствующему value. Несоответствие типа, повтор канала и неизвестный канал отклоняют **весь** пакет. Частичный пакет обновляет только перечисленные каналы. Большие u64 не переводятся в float; JS-клиенту понадобится сохраняющий точность JSON-декодер.

Снимок и ответ показывают только подтверждённый префикс. Пока дисковая запись в работе, другой изменяющий запрос получает `busy`; чтение обслуживается. Очередь диспетчера 64, одно изменение в полёте, до 16 сетевых обработчиков. После дисковой ошибки писатель отравлен до перезапуска: новые изменения не поступают в журнал. Подписки/replay для клиентов, capabilities и общий SDK ещё не реализованы.

## KJN v1 — собственный журнал

Файлы `journal/segment-00000001.kjn` и далее с непрерывными номерами. Сегмент до 4 МиБ, до 4096 файлов. Новый запуск/ротация создаёт следующий файл через create_new; существующие сегменты не дописываются при перезапуске и не перезаписываются. Список сегментов ограничен, события читаются последовательно, вся история не помещается в RAM.

| Область | Байты | Представление |
|---|---:|---|
| Заголовок сегмента | 8 | ASCII `KERNJ001`, включает версию |
| Номер сегмента | 8 | u64 LE, совпадает с именем файла |
| Длина записи | 4 | u32 LE, длина sequence+JSON, 9–65536 |
| CRC32 | 4 | IEEE CRC32 над sequence+JSON |
| Позиция события | 8 | u64 LE, глобально непрерывная с 1 |
| Событие | Переменно | UTF-8 JSON с полем event |

События: settings_baseline, boot, source_opened, batch_stored, source_closed, settings_changed, tail_recovered, stopped. Начальная настройка тоже хранится явно, поэтому будущая смена программного default не меняет существующий профиль. CRC обнаруживает случайное повреждение, не доказывает подлинность/защиту от намеренной подмены. Для фиксации каждой записи используется `sync_all`; пакетирование нескольких подтверждений, сжатие и резервный писатель отложены. При старте журнал проигрывается для восстановления каталога/счётчиков/настройки и последних значений; значения становятся recovered, сессии закрыты.

Неполная последняя запись допускает продолжение в новом сегменте. `tail_recovered` содержит номер старого сегмента, длину целого префикса и длину исходного файла. При следующем чтении эта граница обязана совпасть; произвольно пропустить старую повреждённую запись нельзя. CRC/неверная длина/разрыв последовательности не считаются обычным неполным хвостом.

`recover` копирует логические события целого префикса в новый профиль с сохранением номеров событий, не побайтовый образ исходных сегментов. При копировании остаётся всё необходимое для реализованного raw-среза; карт/вычислительных состояний пока нет. Ошибка структурной проверки может оставить неполную папку назначения и ненулевой код выхода: она не объявляется успешным восстановлением.

## Следующий обязательный компонент

Оболочка будет отдельным процессом и клиентом этого контракта. Пока реализованы точечные чтение/изменение настроек, без подписок и надзора. Перед автозапуском оболочки нужны контракты её желаемого состояния, проверки основного UI-обработчика, ограниченного restart/safe mode и восстановления соединения. Факт наличия TCP не доказывает готовность этих механизмов.

Приём сохраняет календарное время и монотонное смещение внутри boot. После медленного sync свежесть считается от приёма, не от завершения дисковой записи; отсутствие старого монотонного поля при чтении не превращает историю в свежие измерения.
