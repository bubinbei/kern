# Ядро КЕРН: руководство без специальных знаний

Версия 0.1.0. Работают ядро с командной строкой, отдельный тестовый источник и нативная оболочка Windows с меню/настройками/управлением пакетами. Первый COM-источник [im2480](IM2480.md) подключён. Первый сквозной прототип уже добавляет redb, интерпретатор калибровок, графики uPlot, CSV и резерв: [запуск и контракт](PROTOTYPE.md). Ниже сохранено объяснение базового raw/KJN-среза; физическое оборудование ещё не принято. [Проверенные результаты и ограничения](CORE_VALIDATION.md).

## Что мы называем ядром

Представьте диспетчерскую с журналом. Разные приборы передают показания. Диспетчер проверяет, от кого они пришли, какой канал обновился и не повторяется ли пакет. Затем сохраняет показания и только после подтверждения диска сообщает источнику: «Сохранено».

У ядра две разные задачи: хранить последние известные значения для быстрого просмотра и вести историю всех принятых изменений. Таблица последних значений похожа на табло; журнал — на ленту событий. По одному табло восстановить историю нельзя.

```mermaid
flowchart LR
    S[Отдельный источник] --> V[Проверка ядром]
    V --> W[Запись и подтверждение диска]
    W --> T[Обновление таблицы и ответ источнику]
    W --> H[Журнал истории]
    H -. следующий этап .-> I[Интерпретатор]
    I -.-> P[Физические параметры]
    P -.-> U[Оболочка, графики, рабочие файлы]
```

Сплошные стрелки уже работают. Пунктир — следующие этапы. Не превращаем сырое число в тонны без карты: сейчас таблица физических параметров намеренно пустая.

## Как запустить

Уже собранный локальный комплект находится в `dist/Kern-Core-0.1.0/`. В нём:

1. `Start-Core.cmd` запускает ядро и оставляет его консоль открытой.
2. `Run-Demo.cmd` во второй консоли передаёт 100 тестовых пакетов по 6 каналов.
3. `Status.cmd` показывает состояние.
4. `Stop-Core.cmd` штатно останавливает ядро.

Эти команды работают с собственным профилем `data/default` внутри комплекта. Никаких реальных приборов и COM-портов DEMO не открывает. Не закрывайте консоль ядра крестиком во время обычной работы: используйте штатную остановку; крестик считается аварийным завершением.

Если собираете из исходников, откройте PowerShell в корне KERN:

```powershell
cargo build --workspace --release --locked
.\target\release\kern-core.exe serve --profile .\runtime\first-test
```

Первое окно оставьте работающим. Надпись `READY` означает, что ядро загрузило журнал, записало начало нового запуска и готово принимать команды. Во втором PowerShell:

```powershell
.\target\release\kern-demo.exe --profile .\runtime\first-test --id demo-1 --channels 6 --count 100 --period-ms 100
.\target\release\kern-core.exe status --profile .\runtime\first-test
.\target\release\kern-core.exe snapshot --profile .\runtime\first-test
```

Путь профиля должен совпадать во всех командах. Профиль — отдельная папка с настройками, журналом и служебными файлами одного ядра. Второе ядро с тем же профилем не запустится; другой профиль допускается.

## Что означают числа

DEMO создаёт **искусственные целые числа**, не физические измерения. Формула: `seed + номер_пакета × 100 + номер_канала`, где seed по умолчанию 1000. Первый пакет содержит 1100–1105. В сотом — 11000–11005. Это простой эталон: можно независимо проверить каждое значение.

На новом профиле после этого запуска ожидаются `raw_batches: 100` и `raw_samples: 600`. Повторный запуск добавит ещё данные, а не обнулит историю. Когда DEMO закончит работу, источник закроет свою сессию: `active_sources` станет 0, последние значения останутся с качеством `disconnected`. Это штатное завершение источника, а не потеря записей.

Вывод пока в JSON — структурированном тексте. Слева имена полей, справа значения:

| Поле | Понятное значение |
|---|---|
| `boot` | Номер запуска этого профиля |
| `event_sequence` | Позиция последнего события, подтверждённого диском; учитывает и настройки, и подключения |
| `raw_batches` / `raw_samples` | Сколько пакетов / отдельных показаний уже сохранено |
| `source_count` / `active_sources` | Зарезервированные источники / открытые сессии; открытая сессия сама по себе не означает свежих данных |
| `pending_write` | Есть запись, для которой ещё нет подтверждения диска |
| `disk_error` | Ошибка записи; `null` означает, что такой ошибки не обнаружено |
| `catalog_revision` | Версия каталога источников; меняется при открытии/изменении описания источника |
| `settings_revision` | Версия настроек самого ядра |
| `interpreter_connected` / `shell_connected` | Сейчас `false`: эти компоненты ещё не реализованы |

`snapshot` показывает сами каналы. `parameters: []` означает пустую таблицу физических параметров; это не ошибка чтения сырых данных.

## Качество важнее красивой цифры

| Метка | Как её читать |
|---|---|
| `good` | Источник передал нормальное показание, срок свежести не истёк |
| `bad` | Источник пометил показание как недостоверное |
| `missing` | У канала нет значения либо источник явно сообщил пропуск |
| `stale` | Значение осталось, но давно не обновлялось |
| `disconnected` | Сессия источника штатно закрыта |
| `recovered` | Значение прочитано из истории после запуска ядра; новым измерением оно не считается |

Одинаковые числа могут быть разными измерениями. Если прибор прислал ещё один отсчёт 1000 с новым номером пакета, свежесть обновляется. Если он молчит, ядро не создаёт фиктивные отсчёты 1000. Свежесть считается отдельно для каждого канала, поэтому обновление одного не освежает соседние.

Время измерения и время приёма сохраняются отдельно. Срок свежести определяется монотонными часами процесса: перевод системных часов не должен продлевать жизнь старому показанию. После перезапуска старые значения получают `recovered`.

## Почему каналы не перепутаются

Каждому источнику резервируется 100 адресов, но в таблицу передаются только занятые. Первый источник может использовать 18 каналов, второй 20. Если первому добавить ещё 6, адреса второго не изменятся. Первоначальный предел — 10 источников; идентификаторы не перенумеровываются и отключённые места автоматически не переиспользуются.

Имя источника — устойчивый ID, `session` — номер его подключения, `sequence` — номер пакета в этой сессии. Старый процесс не сможет продолжить писать от имени нового подключения. Точная повторная отправка последнего пакета подтверждается без второй записи; тот же номер с другим содержимым отклоняется. Пропуск номера тоже отклоняется явно. Более старые повторы не вставляются заново и не считаются успешным новым вводом.

Ресурс подключения имеет одного владельца. Пока проверяется логическое владение именем ресурса; реальный COM и автоматическое управление приборными плагинами — следующие этапы.

Если окно DEMO закрыли до штатного завершения, ядро не угадывает, можно ли отдать его имя другому процессу: появится `stale`, а повторное открытие даст `resource_busy`. В snapshot найдите текущий session и явно закройте его. Например, только если там session=1:

```powershell
.\target\release\kern-core.exe close --profile .\runtime\first-test --source demo-1 --session 1
```

Либо штатно перезапустите ядро: сохранённые данные останутся, старые сессии закроются. Автоматический надзор источников добавим отдельно.

## Как менять настройки без случайного затирания

Сейчас доступна одна настройка: через сколько миллисекунд канал считать устаревшим. Посмотрите `settings_revision` в status. Для нового профиля это 0:

```powershell
.\target\release\kern-core.exe settings --profile .\runtime\first-test --expect-revision 0 --stale-ms 2000
```

Ядро сначала проверит запрос, затем запишет настройку в журнал и подтвердит новую версию 1. Если другой клиент уже изменил настройки, старая версия 0 не подойдёт: получите `revision_conflict`. Это защита от ситуации, когда одно окно незаметно затирает изменения другого. Перечитайте состояние и осознанно повторите с текущей версией.

Допустимый срок — 100–3 600 000 мс. Эта настройка относится к свежести, а не к частоте опроса или записи. Карты калибровок и их отдельные границы активации появятся с интерпретатором.

## Остановка, проверка и восстановление

Штатная остановка тоже записывается в журнал:

```powershell
.\target\release\kern-core.exe stop --profile .\runtime\first-test
.\target\release\kern-core.exe check --profile .\runtime\first-test
.\target\release\kern-core.exe dump --profile .\runtime\first-test
```

`check` проверяет журнал; `dump` печатает события по одному в JSON Lines, без загрузки всей истории в память. Проверка, выгрузка и копирование восстановления выполняются **при остановленном ядре**: профиль блокируется от параллельной записи.

Если процесс оборвался посередине последней записи, ядро сохранит старый файл как есть, прочитает целые записи и начнёт новый сегмент с отметкой восстановления. Если контрольная сумма целой записи не совпадает, обычный запуск остановится: это может быть повреждение уже сохранённых данных, его нельзя молча выдать за нормальный хвост.

Контрольная сумма CRC — проверочное число, рассчитанное по содержимому записи. Изменение байтов обычно меняет это число и обнаруживается при чтении. Префикс журнала — все целые записи от начала до первой повреждённой; именно его можно сохранить отдельно.

Для такой ситуации есть команда, которая переносит только целый префикс истории в **новую** папку:

```powershell
.\target\release\kern-core.exe recover --profile .\runtime\first-test --output .\runtime\recovered-copy
.\target\release\kern-core.exe check --profile .\runtime\recovered-copy
```

Папка назначения не должна существовать. Исходные файлы не изменяются. Повреждённые и следующие за ними записи не восстанавливаются «по догадке»; это сохранение доступного префикса, а не обещание вернуть все данные. Некоторые структурные ошибки, например отсутствующий сегмент или повторный обрыв самой границы восстановления, пока требуют отдельного разбора и могут быть отвергнуты даже этой командой. Не удаляйте оригинал.

## Что происходит при отказе диска

Запись выполняет отдельный поток. Диспетчер может отвечать на status, пока диск занят. Изменения становятся видны в таблице только после успешного `sync_all` и подтверждения писателя. Если клиент не дождался ответа, результат неизвестен: пакет мог сохраниться. Повторите **тот же** пакет с тем же номером, не придумывайте следующий.

При ошибке записи `disk_error` становится явным, новые изменения не подтверждаются и не накапливаются без предела. Старые значения продолжают стареть. Команда остановки доступна, но сообщает ошибку диска вместо ложного подтверждения новой сохранённой записи. После этого нужно проверить накопитель и журнал; самопроизвольного «всё снова хорошо» пока нет.

Очередь команд — 64, ожидающая запись — одна, сетевых обработчиков — не более 16. Запрос — до 64 КиБ, снимок — до 512 КиБ. При занятости клиент получает `busy` и повторяет запрос. Эти пределы ограничивают память; бессрочно принимать данные без рабочего диска невозможно.

Журнал разбивается на сегменты до 4 МиБ, предел 4096 сегментов. Каждый запуск начинает новый сегмент. Автоматической очистки и сжатия пока нет; при исчерпании лимита запись явно останавливается. Файловый `sync_all` — запрос ОС сохранить запись, а не доказательство защиты от любого отказа питания/контроллера. Полноценные испытания накопителя ещё нужны.

## Первое меню уже подключено

`Start-Kern.cmd` в локальном комплекте запускает ядро и отдельное нативное окно с меню, состоянием, настройкой свежести и списком пакетов. Выберите синтетический источник и нажмите «Запустить»; для завершения источника — «Остановить». Закрытие окна сохраняет работу ядра; повторное открытие — `kern-core shell --profile PATH`. Полная остановка KERN отдельная. CLI/headless-команды выше остаются действующими.

Пакет — папка с `plugin.json` и `.exe`, копирование не запускает код. Контракт/надзор/ограничения и отдельный план операторской веб среды: [PLUGINS](PLUGINS.md). Подписки, интерпретатор и общий SDK впереди.
