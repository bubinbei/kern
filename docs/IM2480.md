# Плагин im2480

Первый источник COM-данных KERN: отдельный Rust-процесс **im2480**, пакет `plugins/im2480`. Ядро и оболочка не открывают COM. Прочитанные каналы поступают через существующий IPC и становятся видны после подтверждения журнала ядром. Интерпретатор калибровок пока не реализован; драйвер не пересчитывает АЦП в тонны/давление и не смешивает источник с DEMO.

## Установка и настройка

После `cargo build --workspace --release --locked` команда `python tools/package_core.py` добавляет пакет в локальный комплект. Состав: `plugin.json`, `im2480.exe`, `config.example.json`, локальный `config.json`. Имена файлов и папок ASCII. Установка/запуск — обычный каталог плагинов оболочки; автоматического опроса после копирования нет. Шаблон намеренно содержит пустой порт: прежде чем нажать «Запустить», выберите свой порт в `config.json`. Упаковка сохраняет существующий конфиг. Рабочие настройки, COM-журналы и измерения не включаются в Git.

`config.json`: `schema=1`, стабильный `source_id`, `port`, `baud`, `timeout_ms`, `poll_interval_ms`, список `modules` с `address` и **явным постоянным `slot`**. Один экземпляр плагина — один COM; другой источник требует другого ID и другого COM. Плагин не устанавливает виртуальные порты и не закрывает чужие процессы.

- Адреса 1–247, включая 200; дубликаты запрещены. До 16 модулей, слоты 0–15 уникальны.
- Каждый слот резервирует 6 номеров внутри 100 каналов источника: `slot*6 + 0…5`. Модули в слотах 0 и 3 дают #0…5 и #18…23; добавление в слот 10 даёт #60…65. Порядок строк конфигурации не меняет номера. Не переиспользуйте старый слот для другого адреса в том же источнике; после изменений требуется остановить и снова запустить плагин. Программного поиска/уплотнения нет.
- Порт задаётся как `COM1`, `COM33` и т. п.; пути, пробелы, ведущие нули и альтернативные имена не принимаются. Доступ ОС эксклюзивный; ресурс в ядре — нормализованный COM, без префикса типа плагина.
- Линия 8N1 без аппаратного/программного управления потоком. Скорости 1200,2400,4800,9600,19200,38400,57600,115200. Тайм-аут 50–2000 мс, но не меньше физического времени 67 байт ответа плюс 20 мс; при 1200 бод короткий тайм-аут отвергается.
- `poll_interval_ms` 100–60000 — пауза **после полного цикла**, не обещание фиксированной частоты. Медленные/молчащие приборы удлиняют цикл. Срок свежести ядра настраивается отдельно с учётом реального времени обхода.

Проверка конфига без открытия COM: `im2480.exe check --config config.json`. Прямой запуск: `im2480.exe run --profile PATH --config config.json`; `--cycles N` ограничивает число циклов для испытания, 0 означает непрерывный опрос. CLI запускайте из папки пакета либо с полными путями. Общие настройки через GUI плагина/сканирование адресов — следующие функции, сейчас используется конфигурационный файл.

## Контракт чтения

Новая реализация использует только **FC03** Modbus RTU. Перед каждой выборкой читает 10 регистров с 0000: идентификатор `494D/2480` и порядок данных `0009=0`. Другой идентификатор/порядок отвергается явно. Затем читается блок `0400…041E`, 31 регистр. Адрес, функция, byte count, CRC и конечность float проверяются. Ответ до 67 байт, конфиг до 16 КиБ; произвольная длина ответа не используется для выделения памяти. В прибор ничего не записывается.

Поддержан ограниченный профиль уже используемого тестового эмулятора, не все варианты оборудования:

| Канал слота | Данные | Тип ядра |
|---|---|---|
| 0,1,2 | Коды А1–А3 из 0401…0403 | unsigned, без калибровки |
| 3 | ДОЛ из 0410/0411, младшее слово первым | signed, точный int32 |
| 4,5 | Частоты из 0412…0415, порядок 0009=0 | float, точное расширение исходного f32 в f64 |

Это декодирование транспорта, а не инженерный расчёт. Другие регистры блока (температура, дополнительные счётчики/статус и приведённые аналоги) пока не публикуются и не сохраняются как полный сырой кадр; журнал содержит выбранные 6 каналов. Поддержка другого порядка слов и дополнительных каналов требует отдельного согласованного профиля.

При тайм-ауте/CRC/неверном адресе/exception/неподдержанном порядке **только шесть каналов этого модуля** передаются как missing, без выдачи старого значения за новое. Следующий адрес всё равно опрашивается. Неконечная отдельная частота становится missing, остальные каналы сохраняют своё качество. Между запросами выдерживается пауза RTU; после ошибки — дополнительный тайм-аут и очистка RX. RTU не имеет transaction ID: произвольно запоздавший корректный ответ того же адреса невозможно всегда отличить от нового. Это ограничение не маскируется обещанием абсолютной свежести.

Одновременно ожидается подтверждение только одного пакета ядра; `busy`/неопределённый транспортный исход повторяет **тот же пакет** с той же сессией/sequence в ограниченном времени. Новые значения не накапливаются бесконечно. При отказе ядра/диска плагин сообщает ошибку и освобождает COM, а не объявляет входы сохранёнными. Неопределённая регистрация источника не повторяется вслепую: общего request-ID для неё ещё нет.

## Остановка и диагностика

Кнопка «Остановить» передаёт `stop` через stdin. Чтение проверяет остановку с коротким тайм-аутом ОС; COM освобождается перед закрытием сессии ядра. При аварийном kill ядро может удерживать занятую сессию: используйте явную `kern-core close --profile PATH --source ID --session N` либо перезапуск ядра. Автоматического восстановления источника после crash/смены boot пока нет. Обычное исчезновение отдельного модуля не завершает процесс. После отключения самого COM-устройства автоматического переоткрытия порта нет: нужна остановка и повторный запуск.

Диагностика записывается в `profile/plugin-status/<source_id>.json`: PID, состояние, подтверждённые пакеты, опросы/ошибки каждого адреса и последнее успешное время. CLI: `im2480.exe status --profile PATH [--source ID]`. Это неавторитетная диагностическая плашка последней попытки запуска, **не журнал восстановления**; запись статуса не подтверждает сохранность измерений. Ошибка диагностического файла не останавливает сырой тракт. Неудачный запуск виден как завершившийся процесс в каталоге; подробности — здесь или в stderr прямого CLI.

Безопасная часть библиотеки запрещает unsafe; только `native_port.rs` содержит небольшую границу системного Win32 COM. Новых registry-зависимостей нет: используются уже имеющиеся официальные `windows-sys`/`windows-link`. Это Windows-срез, macOS и USB/RS485 не приняты.

## Доказательства и происхождение

Реализация и Python-ответчик написаны заново; старый runtime-код, профили, бинарники и частные исследования в репозиторий не переносились. Выбор шести каналов и ограниченного порядка — контракт тестовой интеграции с эмулятором владельца, не заявление о поддержке всех режимов реального прибора. Публичные основания транспорта: [Modbus Application Protocol](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf), [Modbus specifications](https://www.modbus.org/modbus-specifications), [Windows COM handles](https://learn.microsoft.com/en-us/windows/win32/devio/communications-resource-handles), [Windows timeouts](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-commtimeouts).

`cargo test --workspace --locked` проверяет конфиг/резервы, CRC, фрагменты, повреждения/тайм-ауты, типы и конечность. `python tools/validate_im2480.py --ports COM3 COM33` использует **только явно выбранную свободную com0com-пару**, свой профиль и независимый Python-ответчик; пользовательский эмулятор не меняется. [17 сквозных проверок](validation/im2480-0.1.0.json). Отдельно через уже запущенный эмулятор подтверждены 5 модулей / 30 каналов / 10 пакетов / 60 показаний с независимым чтением журнала; его настройки не менялись. [Живая интеграция](validation/im2480-live-0.1.0.json). Это короткий виртуальный стенд, не физическая/длительная/Windows10/слабая аппаратная приёмка.
