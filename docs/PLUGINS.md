# Плагины и обязательная оболочка

Реализован первый [каталог параметров, наборы и расчёты](PARAMETERS.md): библиотека определений processor, предпросмотр/сравнение и свои наборы, ручные значения и готовые операции graph-v1. Рабочие версии принадлежат ядру, исполнение — Rust-интерпретатору; UI встроен в текущий host, универсальный SDK впереди. Дальнейшая схема — [план](PARAMETER_PRESETS_PLAN.md).

Пакет im2480 теперь добавляет вкладку «Модули» в общий host: это конкретное встроенное расширение с проверкой наличия пакета в реестре, а не общий загрузчик веб плагинов. COM остаётся у отдельного Rust-процесса; только он принимает команды из ограниченного локального mailbox. Связи параметров являются версиями карт ядра, а конфигурация линии пока имеет отдельную локальную историю. Полный контракт — [IM2480](IM2480.md).

Реализован первый нативный desktop-срез Windows: отдельный процесс `kern-shell`, меню, статус ядра, настройка срока свежести, список/запуск/остановка дополнительных процессов. Приём, таблица и обязательный журнал остаются в ядре. В отдельном сквозном прототипе подключены Rust-интерпретатор, host uPlot, CSV и backup; запуск и ограничения — [PROTOTYPE](PROTOTYPE.md). Первый COM-источник [im2480](IM2480.md) подключён отдельным пакетом; физические приборы ещё не приняты.

Утверждено: redb — внутренняя зависимость ядра, uPlot — библиотека отдельного пакета графиков с Rust-host. uPlot встроен в нативный пакет `charts`: отдельный Rust-host с ограниченным локальным HTTP bridge. Окно использует установленный Edge/Chrome в режиме приложения; окончательный WebView и универсальный веб SDK ещё не выбраны. Интерпретатор, рабочие писатели и независимый backup — отдельные процессы; база доступна только через ядро. План трёх наборов, истории и восстановления: [STORAGE_CHARTS_PLAN](STORAGE_CHARTS_PLAN.md).

Целевая граница «Настройки параметров» — самостоятельный плагин редактирования параметров и карт. Сейчас это отдельный веб модуль parameter-settings.js внутри процесса/пакета charts, а не отдельный устанавливаемый пакет. Таблица, график зависимости, панорамирование и масштабирование относятся к этому модулю; проверка/версии карт и сохранение остаются у ядра. Панорамирование/масштаб — локальное состояние вида, не изменение калибровки.

Будущие сетевые рабочие места используют общие веб экраны: браузер либо KERN-клиент без источников/локального авторитетного расчёта. Отдельный веб шлюз предоставляет ограниченный API; он не заменяет обязательную системную оболочку и не получает право обходить ядро. Просмотр и офисный сервис — разные полномочия, установка плагинов — отдельное право. Текущий загрузчик/IPC таких режимов ещё не поддерживает. Этапы и границы: [NETWORK_PLAN](NETWORK_PLAN.md).

## Как выглядит установка

Плагин — **папка**, а не DLL, загруженная внутрь ядра. Например:

```text
plugins/
  synthetic/
    plugin.json
    kern-demo.exe
    ... собственные ресурсы пакета
```

`plugins/synthetic/plugin.json` в исходниках — образец. Исполняемый файл туда добавляет локальная упаковка, в Git бинарника нет. Перенесите готовую папку в `plugins` рядом с `kern-core.exe`, нажмите «Обновить список», выберите пакет и «Запустить». Можно задать другую папку через `run --plugins PATH`. Удалять/обновлять пакет следует после остановки его процесса; работающая запись каталога сохраняется до остановки и нового сканирования. Простое копирование ничего не запускает. Архивный установщик, скачивание, зависимости пакетов и постоянный автозапуск пока не реализованы.

Описание содержит `schema`, стабильный `id`, читаемое `name`, `version`, совместимый `protocol`, относительный `executable`, массив `args`. Ядро само добавляет `--profile`; пакет не может подменять этот аргумент. Один ID — один установленный экземпляр; для нескольких источников нужны разные ID и разные ресурсы/порты. Пока пакеты запускаются и останавливаются вручную, выбранное состояние не сохраняется между запусками ядра.

Пределы: 32 записи в папке, манифест до 16 КиБ, до 16 аргументов по 1024 байта, относительный путь к `.exe` внутри пакета. Неизвестные поля, несовместимая версия, выход пути наружу и дубликаты ID отвергаются. Ошибка каталога не останавливает сырой журнал. Это проверка формата, **не песочница**: нативный плагин — доверенная локальная программа с правами пользователя; общий IPC-токен ещё не разделён на capabilities. Не устанавливайте непроверенный код. Подписи и изоляция полномочий — последующие задачи.

## Кто запускает интерфейс

`kern-core run --profile PATH` запускает обязательный соседний `kern-shell.exe`. В списке это `kern.shell`: отключить его кнопкой остановки нельзя. Крестик закрывает окно, ядро продолжает работу. Явное повторное открытие: `kern-core shell --profile PATH`. `serve` остаётся отдельным headless-режимом для испытаний и будущего служебного запуска. Если обязательного файла нет, desktop-запуск сообщает ошибку; тихой подмены нет.

Оболочка опрашивает состояние раз в секунду через рабочий IPC-поток; окно не ждёт диска/сети. Перерисовывается изменившийся текст/список, постоянного графического цикла нет. Нативная оболочка использует системные Win32/GDI-контролы через официальные bindings `windows-sys`; web runtime не включён. Участки `unsafe` ограничены границами ОС: Win32 UI в `crates/shell/src/native.rs` и COM в `crates/im2480/src/native_port.rs`. Ядро, протокол, загрузчик, demo и библиотека декодирования IM2480 запрещают unsafe. Полная проверка памяти, Windows10 и слабого железа ещё впереди. DPI — системный при запуске, без собственной динамической смены масштаба между мониторами.

Основной UI-обработчик порождает heartbeat; просроченные задания heartbeat не отправляются из очереди. Если окно аварийно завершилось либо heartbeat отсутствует более 10 секунд, надзор завершает только свой процесс оболочки и повторяет запуск с задержкой 1 секунда. Не более 3 запусков за 60 секунд, затем safe mode до явного открытия/нового запуска. Обычное закрытие не вызывает respawn. Это первый надзор оболочки, не общая проверка корректности расчётных плагинов.

Прототип добавляет ограниченный restart только управляемых `processor`, `csv`, `backup`, включая надзор lease/прогресса интерпретатора; явная остановка подавляет restart. Это расширение, не обещание надзора произвольного пакета. [Контракт и пределы](PROTOTYPE.md).

Дополнительному процессу передаётся `stop\n` в stdin, затем даётся 2 секунды на выход; после этого завершается только сохранённый дочерний процесс. Синтетический источник поддерживает этот контракт и закрывает свою сессию. Принудительная остановка другого плагина может оставить сессию stale/занятой: нужна явная команда close либо restart ядра. Произвольные дочерние деревья и job-object изоляция пока не поддержаны. Остановка самого ядра завершает запущенные им процессы; это не гарантия получения последней внешней аппаратной выборки. Отдельная ошибка/деталь плагина доступна в IPC-каталоге; полноценный просмотр логов ещё не сделан.

IPC управления: `plugins` → список и диагностическая строка; `plugin_control {id, action:start|stop|rescan}` → accepted/error; `shell_pulse` и `shell_closed` несут сессию конкретного запуска. Очередь управления — 16 запросов, проверка процессов каждые 250 мс в отдельном потоке, без блокировки диспетчера состояния. Каталог/состояние процессов пока оперативные, не часть исторических карт расчёта. Настройка свежести сохраняется прежним версионированным событием журнала.

## Отдельное будущее направление: операторская веб среда

Цель — оператор ГТИ без знания программирования собирает нужные виджеты и экраны, при необходимости с помощью ИИ. Начать с декларативных описаний: параметр, подпись, единица, диапазон, формула из ограниченного набора; затем редактор/шаблоны и веб компоненты. Это цель плана; локальные экраны прототипа уже есть, операторский конструктор и универсальные веб пакеты пока не реализованы.

Ответственные участки — приём оборудования, основной интерпретатор, обязательный журнал и рабочие писатели — остаются Rust-процессами. Веб оболочка/виджеты получают данные через версионированный ограниченный API; прямых ссылок на внутреннюю память и обхода ядра нет. Ошибка экрана не останавливает сбор. Настройки проходят ту же проверку версий и подтверждение ядра. Для u64 необходим контракт без потери точности в JavaScript.

Порядок: redb/карты/replay → стабилизировать API/права/подписки → отдельный прототип графиков uPlot → сравнить RAM/CPU/GPU/прокрутку и отказ с нативным вариантом на слабом Windows-ноутбуке и позднее Mac2012/macOS → принять host и формат веб пакета → отдельно развивать конструктор W1. Библиотека графиков выбрана; WebView/Chromium/фреймворк ещё нет. Обещаний меньшего расхода токенов или ресурсов нет; повторно используемый SDK и шаблоны должны уменьшать объём контекста.

## Проверка этого среза

`cargo test --workspace --locked`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo build --workspace --release --locked`; затем `python tools/validate_core.py` и на Windows `python tools/validate_desktop.py`. Последний проверяет реальные нативные контролы, сохранение настройки, запуск/кооперативную остановку пакета, падение и приостановку UI-потока, бюджет restart, штатное закрытие и независимое чтение журнала. Только новые синтетические профили `target/qa`, без приборов. [Отчёт desktop](validation/desktop-0.1.0.json). Длительная/аппаратная приёмка, power-loss и общий надзор плагинов не завершены.
