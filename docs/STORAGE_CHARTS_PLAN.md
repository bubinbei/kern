# Внедрение redb и uPlot

Статус: утверждённое направление разработки от 2026-10-23, **план, не готовая интеграция**. В текущей сборке остаются KJNv1 и нативная оболочка; redb/uPlot ещё не включены. Ответственные плагины остаются отдельными Rust-процессами. План уточняет [ARCHITECTURE](ARCHITECTURE.md) и очередность [ROADMAP](ROADMAP.md).

## Три таблицы: понятная модель

| Набор | Что содержит | Кто меняет |
|---|---|---|
| 1. `raw_latest` — входы | Последний типизированный отсчёт занятого канала, источник/сессия/последовательность, время и качество | Ядро после проверки и устойчивой записи пакета источника |
| 2. `calibration_versions` — карты | Неизменяемые версии привязок вход → параметр, точек/коэффициентов, единиц, алгоритма и его настроек | Ядро по проверенной команде; интерпретатор проверяет смысл и загружает рабочую копию |
| 3. `parameter_latest` — параметры | Последний подтверждённый результат, качество, ссылки на входы, карту, алгоритм и задание | Ядро после проверки и устойчивой записи результата интерпретатора |

Это три **логических набора**, а не ограничение базы тремя физическими таблицами. Первая и третья таблицы показывают последнее состояние; они не сохраняют историю сами по себе. Интерпретатор не переписывает входы и не открывает файл redb напрямую. Он читает задания/карты через API ядра и возвращает результаты. Графики и рабочие писатели получают параметры; backup дополнительно читает входы, карты и системные события.

Пример карты: raw=1000 → 0 т, raw=8800 → 1 т. Для явно выбранного линейного алгоритма внутри участка: `(raw - 1000) / 7800`. Политика вне диапазона, пропусков, устаревания и осреднения задаётся в карте; значение 0 не подставляется вместо отсутствующего измерения.

## Служебные данные, которые нельзя упустить

- `events`: упорядоченная история принятых входов, результатов, полных версий карт, активаций и изменений настроек. Каждое событие имеет устойчивый ID/номер и версию схемы. Полная карта сохраняется только при создании/изменении, отсчёты ссылаются на неё.
- `registry` и `activations`: постоянные ID/слоты источников и параметров, декларации типов/единиц, сессии и точные границы применения карт. Действует резерв 100 адресов на источник, до 10 экземпляров; пустые каналы не передаются. Один COM — один экземпляр.
- `consumer_positions` и `processor_checkpoints`: подтверждённая позиция каждого интерпретатора/писателя/backup, ожидающие задания и состояние расчётов с памятью. Сердцебиение процесса не заменяет прогресс обработки.
- Индексы истории по каналу/параметру и времени, версия схемы профиля и данные дедупликации. Физический layout выбирается в первом redb-срезе по тестам диапазонного чтения и объёма записи.

Ядро — единственный владелец авторитетного состояния и файла базы. Плагины не обмениваются изменяемыми таблицами друг с другом. В память загружается ограниченное последнее состояние и кэш, история читается порциями с диска.

## Путь одного измерения и изменения карты

1. Источник отправляет пакет. Ядро проверяет владельца, сессию, типы, порядок и повтор. Отдельный дисковый worker сохраняет событие и проекцию входов в одной транзакции redb. После устойчивого commit ядро публикует состояние и подтверждает пакет. Неопределённый ответ допускает повтор того же пакета без второго эффекта.
2. Интерпретатор получает задание из сохранённой истории с точными ссылками на входы и версию карты. Нельзя восстанавливать пропуск из одной последней таблицы: промежуточные отсчёты уже сменились.
3. Ядро проверяет ID задания, сессию, версии, полноту и типы ответа. Результат, проекция параметров, дедупликация и продвижение позиции расчёта фиксируются согласованной транзакцией. Отдельно учитываются история догоняющих результатов и последнее актуальное значение: старый результат не заменяет новый.
4. Писатели/backup читают подтверждённые события и сообщают собственный прогресс. Экран получает снимок с позицией, затем продолжение; после разрыва выполняет пересинхронизацию.

Изменение карты: черновик с expected revision → проверка ядра и интерпретатора → сохранение полной неизменяемой версии → подтверждение загрузки текущей сессией интерпретатора → сохранение активации на точной границе входного журнала → новые задания. Сохранено, загружено и активно — разные состояния. Старые входы рассчитываются по исторической карте, новые — по новой. Политика объединения нескольких источников и качество несовпадающих по времени входов задаются явно; близкие времена не означают синхронное измерение.

Свежесть параметра определяется возрастом исходных измерений и прогрессом расчёта, а не временем получения ответа интерпретатора. Пересчёт старого входа не делает его свежим. Качество входов переносится по явным правилам карты; при зависании расчёта ядро показывает отставание/устаревание параметров, даже если сырые входы продолжают обновляться.

Старые карты не удаляются, пока на них ссылаются сохраняемые входы/результаты/checkpoints/резервные копии. Для воспроизведения нужен также совместимый код соответствующей версии алгоритма; наличие коэффициентов само по себе его не заменяет.

## redb и обязательный журнал

Цель: redb становится внутренним хранилищем ядра, а восстановительный журнал — упорядоченным набором событий в нём. База не устанавливается отдельным отключаемым плагином. Опциональный backup создаёт независимую восстанавливаемую копию; его отказ не отключает основной журнал.

redb предоставляет транзакции и одного одновременного писателя. Для подтверждённых измерений явно используется `Durability::Immediate`; `None` не подходит для обещания сохранности. Это возможности библиотеки, а не результат испытаний KERN. Сбой питания/контроллер диска требует отдельной проверки; принудительное завершение процесса не эквивалентно power-loss.

Нельзя постоянно вести KJN и redb как два равноправных источника истины: сбой между двумя commit оставляет расхождение. Для нового тестового профиля выбирается один backend. Существующий KJN сохраняется неизменным; offline-импорт создаёт новый redb-профиль, проверяет последовательности/значения/метаданные и формирует отчёт. Частичный импорт не становится рабочим профилем. Переключение рабочей поставки — после отказной приёмки и проверенной процедуры возврата. Прежний KJN reader остаётся доступен для чтения/импорта.

Для redb задаются предел кэша, короткие read-транзакции и bounded очередь writer. Долгое чтение/уплотнение/backup не должны бесконтрольно удерживать страницы или тормозить приём. Квоты, ротация по сеансам/сегментам и очистка проверяются до длительной эксплуатации. Отставание обязательного потребителя удерживает нужную историю; при достижении квоты требуется явная политика остановки/потери с диагностикой. Безграничной записи при конечном диске не обещаем.

## Восстановление и два вида записи

**Основной журнал в ядре** сохраняет входы даже при остановленном интерпретаторе. После его перезапуска ядро выдаёт недостающую историю и прежние карты. Для осреднения/накопления нужен checkpoint либо достаточная предыстория. Надзор учитывает прогресс рабочего обработчика, дедлайн задания и новую сессию, ограничивает перезапуски; поздние ответы прежнего процесса отвергаются.

**Плагин рабочих файлов** получает параметры, поддерживает обычный/быстрый потоки с отдельными периодами/наборами каналов. Он обязан иметь восстанавливаемую позицию. Одной записи позиции в redb недостаточно для файла: падение между записью файла и ack создаёт неопределённость. Нужны устойчивые ID записей либо атомарные проверяемые блоки, из которых писатель определяет уже записанную границу. Это отдельная приёмка C4.

**Плагин backup** читает через ядро события, реестр, исторические карты/активации, результаты, версии схем/алгоритмов и необходимые checkpoints. При позднем подключении сначала догоняет историю, затем продолжает с известной позиции. Сначала независимые несжатые блоки с порядком/контролем целостности; компрессия позднее по измерениям. Копию проверяют восстановлением в пустую папку. Копировать открытый файл redb обычной файловой операцией без протокола согласованного снимка нельзя. Резерв на другом физическом носителе проверяется отдельно.

## uPlot как заменяемый экран

uPlot встраивается в отдельный пакет графиков с веб представлением; ядро, IM2480, интерпретатор и писатели остаются Rust. Существующая нативная системная оболочка сохраняет меню, подключение плагинов и аварийную диагностику. Первый прототип графиков допускает отдельное окно; превращать его во встроенную вкладку и менять оболочку следует после измерений. Веб конструктор для оператора без программирования остаётся отдельным будущим этапом W1.

WebView/браузерный host ещё не выбран. Сначала локальный автономный стенд uPlot, затем выбор host по Windows10, офлайн-поставке, RAM/CPU/GPU и изоляции. JS/CSS поставляются локально в зафиксированной версии, без CDN и обязательного интернета. Токен полного IPC ядра не передаётся произвольным веб компонентам: Rust-host предоставляет ограниченный версионированный bridge с проверкой происхождения, действий, размеров и диапазонов. Нативные плагины пока доверенные, это не обещание песочницы.

Графики получают выбранный интервал и только нужные каналы. Подготовка данных в Rust сохраняет экстремумы, порядок и разрывы; целые u64 передаются без потери точности, например десятичными строками, преобразование для пиксельной координаты не меняет исходник. Флажок ссылается на исходный отсчёт/ID, а не на сглаженную точку экрана. Запрос уточнения значения идёт к исходным данным.

В первом прототипе проверить вертикальную ось времени, несколько кривых в дорожке, согласованное движение сетки/времени, перо в конечной точке, сутки истории, изменение ширины колонок, флажки и курсор. Нельзя считать эти взаимодействия готовыми лишь из-за подключения uPlot. Плиточная сетка/флажки — расширения KERN; обновления по событию, объединение накопившихся изменений, без постоянного полного рендера. Стартовая гипотеза: live до 10 перерисовок/с, взаимодействие до 30; итог по измерениям. Скрытая вкладка не рисуется, после открытия запрашивает актуальное окно.

## Очередность внедрения

| Шаг | Результат | Обязательная приёмка |
|---|---|---|
| R1 | Интерфейс storage; закреплённая redb, лицензии; raw/настройки/реестр на новом синтетическом профиле | Независимый эталон событий/значений; crash до/после commit/ack; одинаковые повторы; ошибка диска/квоты; измерение размера/скорости/памяти |
| R2 | Offline KJN → новый redb-профиль, продолжение после restart, порционное чтение | Полнота и порядок; неполный хвост/порча; прерванный импорт и безопасный повтор; исходник побайтно неизменён |
| R3 | Три набора, версии/активации карт, стандартный Rust-интерпретатор, позиции/replay/надзор | Эталон 1000→0/8800→1; живой heartbeat с зависшим worker; смена карты при backlog; stateful checkpoint; нет повторного эффекта/отката latest |
| R4 | API snapshot/history/subscribe и ограниченный bridge; первый автономный uPlot-прототип | Нет разрыва snapshot/subscribe; ограниченные сообщения/память; 3–6 дорожек, сутки истории, пропуски, u64; остановка экрана не прерывает raw |
| R5 | Рабочий писатель и независимый несжатый backup | Падение между file write/ack; догон без дублей; поздний backup; восстановление из копии без исходного профиля и сравнение с эталоном |
| R6 | Измеренная поставка graph-host, интеграция в оболочку, длительная приёмка | Windows10 и слабый ноутбук Intel «4125»: idle/live/scroll/hidden, CPU/GPU/RAM/диск/задержки отдельно по процессам; 24–72ч; macOS2012 позже |

Первый следующий рабочий срез — **R1**, не одновременная замена всех подсистем. До реализации закрепить измеряемый baseline на одинаковом синтетическом потоке. Успешный build, чужой benchmark и короткий тест на мощном ПК не подтверждают требования слабого стенда. Каждый следующий срез сохраняет проверки отказов предыдущего.

Контекст следующего задания: реализовать R1 для нового синтетического профиля, сохранив KJN reader и работающий комплект; не открывать COM и не переносить реальные профили. Начать с `crates/engine/src/journal.rs`, `crates/engine/src/state.rs`, `crates/core/src/server.rs`, контракта `crates/protocol/src/lib.rs` и существующего `tools/validate_core.py`. Новую зависимость закрепить в Cargo.lock, проверить лицензии/упаковку. Результат — raw-срез на redb с прежними гарантиями ack/повторов и независимым отчётом отказов/ресурсов, без одновременного внедрения интерпретатора или веб оболочки.

## Открытые зависимости и лицензии

- [redb](https://github.com/cberner/redb): MIT OR Apache-2.0; для поставки выбрать MIT. API [транзакций](https://docs.rs/redb/latest/redb/struct.WriteTransaction.html) и [durability](https://docs.rs/redb/latest/redb/enum.Durability.html) сверять с закреплённой версией.
- [uPlot](https://github.com/leeoniya/uPlot): [MIT](https://github.com/leeoniya/uPlot/blob/master/LICENSE), Canvas2D и расширения. Версию и точные артефакты закрепить в R4.

Это разрешительные лицензии для коммерческого использования при сохранении требуемых уведомлений. При фактическом включении обновить реестр зависимостей, исходные тексты лицензий, хеши и упаковку; сейчас установленные зависимости/лицензии комплекта не изменились. Host и новые транзитивные зависимости проверяются отдельно.
