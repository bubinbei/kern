# im2480 plugin

KERN's first COM data source is the separate Rust **im2480** process, packaged under `plugins/im2480`. Core and shell do not open COM. Read channels use existing IPC and become visible after core journal acknowledgement. Calibration interpretation is not implemented; the driver does not convert ADC codes into weight/pressure or mix the source with DEMO.

## Installation and configuration

After `cargo build --workspace --release --locked`, `python tools/package_core.py` adds the package to the local bundle: `plugin.json`, `im2480.exe`, `config.example.json`, and local `config.json`. File/directory names are ASCII. Install/start through the ordinary shell plugin catalog; copying never starts acquisition. The template deliberately has an empty port: set your port in `config.json` before starting. Packaging preserves existing configuration. Working settings, COM logs and measurements are not committed to Git.

`config.json` contains `schema=1`, stable `source_id`, `port`, `baud`, `timeout_ms`, `poll_interval_ms`, and `modules` with `address` and an **explicit permanent `slot`**. One instance owns one COM; another source needs another ID and COM. The plugin installs no virtual ports and stops no other processes.

- Addresses 1–247, including 200; duplicates rejected. Up to 16 modules, unique slots 0–15.
- Each slot reserves six numbers inside the source's 100-channel reservation: `slot*6 + 0…5`. Slots 0 and 3 give #0…5 and #18…23; adding slot 10 gives #60…65. Configuration row order does not change numbers. Do not reuse an old slot for a different address within the same source; configuration changes require stopping and restarting. No automatic discovery/compaction.
- Port names are `COM1`, `COM33`, etc.; paths, spaces, leading zeros and aliases are rejected. OS access is exclusive; the core resource is normalized COM without a plugin-type prefix.
- Line format is 8N1 without hardware/software flow control. Baud choices: 1200,2400,4800,9600,19200,38400,57600,115200. Timeout 50–2000 ms, at least the physical duration of the 67-byte response plus 20 ms; short timeouts at 1200 baud are rejected.
- `poll_interval_ms`, 100–60000, is a pause **after a complete cycle**, not a fixed-rate guarantee. Slow/silent devices lengthen the cycle. Configure core freshness separately for the actual traversal time.

Validate without opening COM: `im2480.exe check --config config.json`. Direct run: `im2480.exe run --profile PATH --config config.json`; `--cycles N` limits test cycles, zero means continuous polling. Run CLI from the package directory or supply full paths. Plugin configuration GUI/address scanning are later functions; this slice uses a configuration file.

## Read contract

The independent implementation uses Modbus RTU **FC03 only**. Each sample first reads ten registers from 0000 to check identity `494D/2480` and data order `0009=0`. Other identities/orders are explicitly rejected. It then reads `0400…041E`, 31 registers. Address, function, byte count, CRC and finite floats are checked. Responses are bounded to 67 bytes, config to 16 KiB; arbitrary response lengths never drive allocation. No device writes are sent.

This is a restricted profile for the existing test emulator, not every hardware variant:

| Slot channel | Data | Core type |
|---|---|---|
| 0,1,2 | A1–A3 codes from 0401…0403 | unsigned, uncalibrated |
| 3 | DOL from 0410/0411, low word first | signed, exact int32 |
| 4,5 | Frequencies from 0412…0415, order 0009=0 | float, exact widening of source f32 to f64 |

This is wire decoding, not engineering calculation. Other block registers—temperature, extra counters/status and converted analog values—are not yet published or archived as a complete raw frame; the journal contains the six selected channels. Other word orders/additional channels need a separately agreed profile.

Timeout/CRC/wrong address/exception/unsupported order marks **only that module's six channels** missing, without presenting an old value as a new sample. The next address is still polled. A non-finite individual frequency becomes missing while other channels retain their quality. RTU gaps are observed; errors add a response-timeout delay and RX purge. RTU has no transaction ID: an arbitrarily delayed valid response from the same address cannot always be distinguished from a fresh response. No absolute freshness guarantee conceals this limitation.

Only one batch awaits core acknowledgement; `busy`/uncertain transport outcomes retry **the same batch** with identical session/sequence within bounded time. Fresh readings do not accumulate indefinitely. Core/disk failure is reported and COM released, without claiming inputs were saved. An uncertain source registration is not blindly repeated; it has no general request-ID deduplication yet.

## Stop and diagnostics

The stop button sends `stop` on stdin. Reads check shutdown using short OS timeouts; COM is released before closing the core session. Forced kill can leave an occupied core session: explicitly use `kern-core close --profile PATH --source ID --session N` or restart the core. Automatic source recovery after crash/new boot is not implemented. A single missing device does not terminate the process. Unplugging the COM device does not automatically reopen its handle: stop and start again.

`profile/plugin-status/<source_id>.json` contains PID, phase, acknowledged batches, per-address polls/errors and last successful time. CLI: `im2480.exe status --profile PATH [--source ID]`. This is non-authoritative diagnostics for the latest launch attempt, **not a recovery journal**; writing status does not acknowledge measurement durability. Diagnostic-file failure leaves raw acquisition running. Failed launch appears as an exited catalog process; details are available here or from direct CLI stderr.

The safe library forbids unsafe; only `native_port.rs` contains a small Win32 COM boundary. No registry dependencies were added: existing official `windows-sys`/`windows-link` are reused. This is a Windows slice; macOS and USB/RS485 are not accepted.

## Evidence and provenance

Implementation and Python peer were written afresh; old runtime code, profiles, binaries and private research were not imported into this repository. The six-channel/order choice is a test integration contract with the owner's emulator, not support for all real-device modes. Public transport references: [Modbus Application Protocol](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf), [Modbus specifications](https://www.modbus.org/modbus-specifications), [Windows COM handles](https://learn.microsoft.com/en-us/windows/win32/devio/communications-resource-handles), [Windows timeouts](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-commtimeouts).

`cargo test --workspace --locked` covers config/reservations, CRC, fragments, corruption/timeouts, types and finiteness. `python tools/validate_im2480.py --ports COM3 COM33` uses **only an explicitly selected free com0com pair**, its own profile and independent Python peer; the operator emulator is untouched. [17 end-to-end checks](../validation/im2480-0.1.0.json). Separately, the already-running emulator supplied 5 modules / 30 channels / 10 batches / 60 samples, confirmed by an independent journal reader, without settings changes. [Live integration](../validation/im2480-live-0.1.0.json). These are short virtual tests, not physical/endurance/Windows10/weak-hardware acceptance.
